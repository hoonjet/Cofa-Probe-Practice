AI 해커톤 단계별 프롬프트 실제 응답 시뮬레이션 (IT 백엔드 디버깅)

과제 상황 (도메인: IT 백엔드 디버깅 - 장애 해결)
귀하는 사내 백오피스 주문 서비스를 담당하는 백엔드 엔지니어입니다. 고객별 주문 목록을 조회하는 API(GET /orders)에서 특정 조건에 간헐적 HTTP 500 오류가 발생하며, 전체적인 응답 지연과 DB 부하가 관측되고 있습니다. 제공된 에러 로그(server_error.log), 코드 조각(Legacy_Code.pdf), DB 쿼리 트레이스(db_query.csv)를 분석하여 근본 원인을 규명하고 성능을 개선해야 합니다.

제약 조건 (환경): 제공된 자료에는 개발자 실명, 이메일 등 민감한 개인정보가 포함되어 있습니다. AI 모델은 한 번에 모든 파일을 깊이 있게 분석할 수 없으며, 분석 결과는 반드시 파일명과 행 번호를 인용하여 증명해야 합니다.

🛠️ Step 1. 가드레일 설정 및 에러 추적 (Cross-Validation)

로그와 코드 파일을 연결하여 정확한 에러 발생 지점과 조건을 추적합니다.

❌ [나쁜 프롬프트 (미흡한 사례)]

"첨부된 에러 로그랑 코드 보고 500 에러 왜 나는지, 어떻게 고치는지 알려줘."

감점 사유: 보안 지시(개인정보 마스킹)가 누락되었고, 근거 인용을 지시하지 않아 AI가 추상적인 원인을 꾸며낼(Hallucination) 위험이 큽니다.

✅ [좋은 프롬프트 (우수 사례)]

"너는 사내 백엔드 시니어 엔지니어로서 장애 원인을 분석해야 해. 작업을 시작하기 전에 [보안 규칙]을 절대적으로 지켜. 분석 결과에 개발자 실명이나 이메일이 포함될 경우 반드시 마스킹(예: 홍, a*@company.com) 처리해 줘.

첨부된 server_error.log의 스택 트레이스(Stack Trace)를 분석하고, 이를 Legacy_Code.pdf의 GET /orders 라우트 코드 로직과 대조해 줘.

간헐적인 500 오류가 어떤 특정 입력값이 들어왔을 때 소스 코드의 어느 라인을 거치며 터지는지 실행 경로를 역추적해 줘.

분석 결과는 반드시 근거가 된 로그의 행 번호와 소스 코드의 라인 번호를 인용(근거: server_error.log 10행, Legacy_Code.pdf 21행)하여 설명해 줘."

🛠️ Step 2. 성능 병목 정량 분석 (Metrics & Evidence)

DB 쿼리 로그를 통해 성능 저하의 원인을 숫자로 증명합니다.

❌ [나쁜 프롬프트 (미흡한 사례)]

"첨부된 db_query.csv 보니까 API 응답이 엄청 느린데, DB가 왜 느린지 분석해 줘."

감점 사유: 구체적인 지표 요구가 없어 AI가 "쿼리가 무겁습니다", "트래픽이 많습니다" 식의 표면적인 답변을 낼 가능성이 높습니다.

✅ [좋은 프롬프트 (우수 사례)]

"첨부된 db_query.csv와 schema_short.pdf를 교차 분석해서 DB 부하 원인을 정량적으로 증명해 줘.

트레이스 로그를 분석하여 1회 API 호출당 특정 쿼리(예: order_items 조회)가 반복 실행되는 횟수(N+1 문제 여부)를 세어 줘.

해당 반복 쿼리들의 처리 시간(duration_ms)을 모두 합산하여, 전체 지연 시간 중 병목이 차지하는 비율을 정량적 근거(행 번호 포함)로 제시해 줘.

schema_short.pdf를 확인하여 위 쿼리와 관련된 인덱스(Index) 누락 여부를 확인해 줘."

🛠️ Step 3. 개선안 도출 및 방어적 테스트 설계 (Technique & Cognition)

분석된 원인을 해결하는 코드를 작성하고, 재발 방지를 위한 테스트 케이스를 설계합니다.

❌ [나쁜 프롬프트 (미흡한 사례)]

"앞에서 찾은 에러랑 성능 문제 고친 파이썬 전체 코드 새로 짜줘."

감점 사유: AI에게 코드 전체를 다시 짜라고 하면 기존 비즈니스 로직을 누락할 수 있으며, 스스로 코드를 검증하려는 노력(인지 관리)이 보이지 않습니다.

✅ [좋은 프롬프트 (우수 사례)]

"앞서 분석한 [500 에러 분석 결과]와 [DB 성능 병목 분석 결과]를 해결하기 위한 백엔드 개선안을 작성해 줘.

핵심 코드 블록 제안: 전체 코드가 아닌, 기존 로직을 어떻게 수정해야 하는지 2개의 핵심 코드 블록(입력값 검증 방어 로직 추가, N+1 문제 해결을 위한 쿼리 최적화)으로 작성해 줘.

테스트 케이스 제안: 500 에러를 유발했던 엣지 케이스(Null, 빈 문자열, 타입 오류 등)를 방어할 수 있는 검증용 테스트 케이스를 5개 제안하고, 각 케이스별 '확인 기준(Expected Behavior)'을 명확히 명시해 줘."

[전략 포인트]
AI가 수정해야 할 범위를 '핵심 코드 블록'으로 제한하여 코드 리뷰 역량을 보여주고, 테스트 케이스를 요구함으로써 방어적 코딩(Defensive Coding)과 엣지 케이스에 대한 고려(인지 관리)를 완벽하게 어필합니다. 이 결과물들을 모아 최종 마크다운 보고서로 취합하면 고득점 보고서가 완성됩니다!
